Critical Architecture Rule

VeloxLane never holds vehicle funds.

All car purchase money flows through Escrow.com (licensed in all 50 states). VeloxLane's Stripe account only handles platform fees: listing ($12), unlock ($6), featured upgrades. This eliminates the money transmitter license requirement entirely. Composer must enforce this boundary in every code path — pin it as an always-applied Cursor rule (see § 02) so it can never drift out of context.

Brand-Defining Feature

Every listing photo becomes a VeloxLane billboard.

When a seller captures photos, AI detects the license plate and overlays a branded "dealer-style" VeloxLane plate in its place. Two wins in one feature: real plates are never exposed to buyers (privacy), and every photo shared, screenshotted, or scraped carries our wordmark (free distribution). Buyers see the original plate only when the deal closes and the bill of sale is signed. See § 07 prompts P2.03 + P2.04 for design and implementation.

§ 02 — Working With Composer

One model. Two tracks. Two passes.

You are building in Cursor with Composer as your main model. The lever isn't which model — it's how you drive Composer. Two tracks: Build runs Composer in Agent mode on well-specified work; Plan + Review runs the hard, high-stakes work through Plan mode first (you approve the written plan before any code), then a separate review pass in a fresh chat. Every prompt in § 07 is labelled with its track. Composer handles filesystem, git, terminal, and MCP servers natively in Agent mode — no plugin required.

◆ Plan + Review

The Architect & Reviewer

Plan mode first, then a review pass in a fresh chat. Reach for it when a mistake is expensive or the problem is genuinely hard.

  • System architecture and database schema design
  • Anything touching money: payments, escrow, webhooks
  • Security work and adversarial code review
  • Legal / compliance: bill of sale, ESIGN/UETA, SOC2
  • The brand-defining differentiators (guided camera, plate cover, dealer detection)
  • Novel design work and the design system itself
  • Every review pass and every phase sign-off gate
▣ Build

The Implementer

Agent mode, straight through. Fast and economical — build well-specified work and iterate quickly.

  • Scaffolding, config, and CI/CD wiring
  • CRUD endpoints and Supabase queries against a known schema
  • UI screens built from the established design system
  • Integrations that follow vendor docs (CARFAX, Twilio, Maps)
  • Tests written against a clear spec
  • Routine mobile screens, deep links, store config
  • Marketing copy and SEO content (brand voice)
The Working Rhythm

Build in one chat. Review in a fresh one.

For each prompt: run the build pass on a feature branch (Build track straight in Agent mode, or Plan track via Plan mode first), open a PR, then run a separate review pass in a fresh Composer chat (new chat, Cmd/Ctrl+N — clean context). Reviewing in a clean context — not the chat that wrote the code — is what makes the review real instead of a rubber stamp. You are the human approver: nothing merges to main without a green CI run, a review-pass sign-off, and your merge. Security, money, and legal work always get a review pass, no matter how they were built — and for those, you can pin a frontier reasoning model in the picker (e.g. Claude Opus 4.7 or GPT-5.5) for the build itself.

Track Rule of Thumb

When in doubt, prototype in Agent mode, harden with Plan + Review.

If a Build-track pass stalls, produces shaky output, or the task turns out subtler than it looked, switch that prompt to the Plan track — plan it first, and if it's money/security/legal-critical, pin a frontier reasoning model for the run. The labels in § 07 are strong defaults, not handcuffs — the deciding question is always "how expensive is a mistake here, and how much genuine reasoning does this need?"

The #1 Cursor Setup Step

Cursor Rules make your invariants un-droppable.

Composer reads project rules from .cursor/rules/*.mdc (and AGENTS.md) and applies the always-on ones to every turn. This matters because Cursor compacts context on long chats — and compaction can silently drop instructions you typed earlier. The fix: the non-negotiables (never hold funds, RLS on every table, real plates never public, no secrets behind public env prefixes, FL/TX only) live in an always-applied rule file, not just in a prompt. Build this before P1.01 (see the P1.00 prompt in § 07).

Three habits that make Composer reliable here: (1) give it context with @-mentions — @blueprint, @packages/db, @.cursor/rules — rather than hoping it remembers; (2) one feature per chat, and start each review pass in a new chat; (3) on Plan-track prompts, read the plan before you let it write code — that 30 seconds is where you catch the expensive mistakes.

Environment Variables & the .env Plan

Secrets are the one thing a leak can't undo. VeloxLane uses a four-tier env strategy so a key is never in the wrong place.

The .env Plan

One committed template. Real values live in four places, never in git.

1. .env.example — committed to the repo, placeholders only (the block below). It's the contract: every key the app reads, documented.
2. .env.local — each developer's machine, git-ignored, filled with test/sandbox keys.
3. Staging — values set in the Vercel staging project env + EAS secrets, all test/sandbox keys (see PRE-05).
4. Production — live keys set in the Vercel production env + EAS secrets, mirrored in 1Password. Never on a laptop.

The one rule that prevents disasters: only variables prefixed NEXT_PUBLIC_ (web) or EXPO_PUBLIC_ (mobile) are bundled into client code and visible to anyone. Never put a secret behind those prefixes. Everything else — service-role keys, secret keys, webhook secrets, AWS credentials — is server-only (API routes + Supabase Edge Functions). Rotate the crown jewels (Supabase service-role, Stripe secret, all webhook secrets, AWS secret) on any suspected leak.

In-App Reference · Build This Into the "Where's My VIN?" Helper

Where to find the 17-character VIN.

The VIN (Vehicle Identification Number) is 17 characters and never uses the letters I, O, or Q (to avoid confusion with 1 and 0). Show sellers these spots, easiest first:

  • Driver-side dashboard — stand outside the car and look through the windshield at the lower corner where the dash meets the glass on the driver's side. This is the most common spot.
  • Driver-side door jamb — open the driver's door and look at the post/pillar where the door latches; there's usually a sticker with the VIN, plus tire and weight info.
  • Vehicle title or registration — the VIN is printed on the title, the registration card, and the insurance card. Fastest if the car isn't handy.
  • Engine bay — stamped on the front of the engine block or firewall on many vehicles (varies by make).
  • Trunk / spare-tire well — some vehicles stamp it under the trunk liner or near the spare.
  • Motorcycles — on the steering neck near the handlebars, or stamped on the engine case / frame.

In the app, pair this list with the Scan VIN button: most sellers can just point the camera at the barcode on the door-jamb sticker and skip typing entirely.
